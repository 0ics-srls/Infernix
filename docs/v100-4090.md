# Qwen3.8-Flash-Next on a V100 + RTX 4090 pair (this fork)

Infernix upstream runs Qwen3.8-Flash-Next (NVFP4 experts) on one RTX 5090 (sm_120a). This fork ports it to a
machine with an **RTX 4090 (sm_89, 24 GB)** and a **Tesla V100 (sm_70, 32 GB)**, used together: the 4090 runs the
Program, the V100 holds and computes routed experts. Branch `i2-v100` (October 2026); `v100-4090` follows it.

## What the fork changes

**Building for sm_89 (CUDA 12.8; CUDA 13 dropped sm_70).** `CMAKE_CUDA_ARCHITECTURES=89`.

- `ops/common/arch.cuh`, `core/device_arch.h`: device and host architecture gates. TMA, mbarrier transactions,
  `setmaxnreg`, block-scaled and FP4 MMA compile with a trap below sm_90/sm_120 and their dispatchers avoid them.
- PDL is a no-op below sm_90; the unit-scale FP8 MMA uses the plain sm_89 `mma.m16n8k32.e4m3`; E2M1 to FP16/FP32
  conversions have software paths with the instructions' exact semantics.
- BF16 TMA linear schedules run their tiles on the `cp.async` MMA kernel (`Bf16CpAsyncTwin`); the GDN gating
  cooperative grid is sized from the driver's occupancy; CUDA 12.8 `cudaMemcpyBatchAsync`; GCC/nvlink fixes.

**The V100 as an expert service** (`ops/offloaded_sparse_moe/cuda/remote_experts.h`).

- A second channel beside the CPU one (`MoeRemoteChannel`, `cpu/remote_request.h`): the 4090's MoE call copies x to
  mapped host memory, flags the experts the V100 holds (`remote_plan_kernel`), computes its own experts and the shared
  expert, then places the V100's outputs (`remote_wait_kernel`). Held experts are never CPU-served, staged or fetched.
- The expert kernels live in a non-RDC archive built for `70;89` (`infernix_offloaded_moe_cuda`), so the V100 runs
  the same exact narrow route: decode outputs are bit-identical to the CPU engine on either GPU.
- Division of the experts by routing frequency (a Strata `STRP` v1 expert profile): the 4090's LFRU cache takes the
  hottest ranks (with RAM copies as its promotion source), the V100 the next ranks, RAM the coldest; the SSD tier's
  ranking ignores the V100's experts.
- V100 kernels for decode: weight slices read from global memory instead of staged in shared memory; the V100's
  copies are permuted at load into a row-pair unit layout (one 16-byte load per lane, `unit_sums_rp`); A4(x) once per
  entry (`act_plane`); pass kernels of 2, 5 and 8 columns sized to the widest job; no stage kernel for all-resident
  calls. Bit-identical to the record path (`bench/ops/remote_experts_bench.cu ... check`).
- **The wide route below sm_120 on WMMA FP16** (both GPUs): experts with more than eight columns (prefill) use FP16
  tensor cores on E2M1 x E4M3 weights and A4 activations (exact in FP16, products exact in FP32), FP32 accumulation,
  FP16 activation planes in the workspace, a register pipeline with K steps of 64. Like the sm_120 FP4 route, only the
  FP32 summation order differs from the exact integer sum.

## Running

```text
INFERNIX_REMOTE_EXPERT_DEVICE=1              # CUDA device of the V100 (the 4090 is device 0)
INFERNIX_EXPERT_PROFILE=expert-profile.bin   # STRP v1 ranking of (layer, expert) pairs, most routed first
INFERNIX_REMOTE_EXPERT_RESERVE_MIB=1536      # memory the V100 keeps free beside the records
infernix Qwen3.8-Flash-Next-NVIDIA-NVFP4-Dense8-Infernix-00001-of-00003.infernix \
  --ngram-volume Qwen3.8-Flash-Next-NVIDIA-NVFP4-Infernix.ngram --device 0 --kv-dtype int8 \
  --max-context 32768 --expert-ram-mib 36000 --expert-state flash-next.expert-state \
  --spec mtp --draft-tokens 4 --lm-head-draft --prompt "..."
```

`--log-level debug` prints the V100 service's times per request (host, uploads, experts, gather) and the CPU
service's. `INFERNIX_ONE_COLUMN_KERNELS=0/1` forces the narrow kernel family.

## Measured (Ryzen 5 5600X, 62 GB DDR4, both GPUs on PCIe Gen3 x8, recipe Dense8, INT8 KV)

| | this fork, V100 + 4090 | Strata (GSQ IQ3_XXS, all experts in VRAM), same machine |
|---|---|---|
| decode, code (MTP) | 86-92 tok/s | 165-205 tok/s |
| prefill, 402-token prompt | 2.9 s (140 tok/s) | ~0.25 s |
| prefill, 8,784-token prompt | 895 tok/s | ~1,700 tok/s |

The limit is capacity, not kernels: the NVFP4 experts are 63 GiB and the two GPUs hold ~44 GiB of them (4090 cache
5,800, V100 11,424), so ~7,400 experts (19.5 GiB) stay in RAM. Decode serves them on the CPU; every prompt touches
nearly all of them, so prefill computes them on the CPU or copies them over PCIe Gen3 x8 (6.7 GB/s): 26.7 GiB were
streamed for the 8.8k prompt. On a machine whose memory holds every expert near the compute, the same port would not
pay this.

## Not done

- Vision on sm_89 (the tower is BF16 in the artifact; untested here).
- The W4A16 experts (orcarouter's uncensored conversion) keep the narrow route at every width.
- FP8 TMA linear routes (recipe C's dense projections) have no sm_89 fallback yet.
- A device-driven V100 service (no host thread per request) and pre-summed V100 outputs for prefill.
